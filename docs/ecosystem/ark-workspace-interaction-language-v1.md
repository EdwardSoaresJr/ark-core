# ARK Workspace Interaction Language v1

**Parent:** [ark-constitution-v1.md](./ark-constitution-v1.md) — constitutional principle: **coherence over capability**  
**Status:** Interaction grammar — apply, do not extend without earned sentences  
**Date:** June 2026  
**Do not:** Code this into a meta-framework yet. Sufficient doctrine exists — apply it.

---

## Architecture vs design philosophy

**Architecture** tells you where code lives.

**Design philosophy** tells you how every future decision should feel.

ARK has moved from the first toward the second. This document is philosophy, not a module map.

Most software keeps inventing principles because existing ones do not help answer the next question. ARK's grammars are **self-correcting** — each is protected by a question that resolves the next decision without a new doctrine document.

**ARK now has a way to discover itself.** That is rarer than any feature.

---

## Four grammars

ARK is not "modules." It is four grammars:

| Grammar | Governs | Protecting question |
| --- | --- | --- |
| **Authority** | Truth | What is true? |
| **Projection** | Audience | Who needs to see it? |
| **Workspace** | Interaction | Which operator question does this answer? |
| **Evolution** | Product improvement | Which repeated sentence earned this change? |

Authority owns operational truth. Projection packages answers for a surface and role. Workspace is how an operator **works** with that truth without losing place. Evolution is how ARK **changes** without rewriting truth from a single opinion.

Observation, Configuration, and Transport remain delivery layers — but the mental model for product decisions is **Truth → Audience → Interaction → Improvement**.

---

## The evolution loop

On paper, ARK ships truth through projection into workspace:

```
Authority → Projection → Workspace
```

In practice, ARK evolves like this:

```
Authority
    ↓
Projection
    ↓
Workspace
    ↓
Operator behavior
    ↓
Repeated sentences
    ↓
Tightening
    ↓
Workspace
```

The full picture:

**Truth**

```
Authority → Observation → Projection
```

**Product**

```
Workspace → Operator behavior → Repeated sentences → Tightening → Workspace
```

### The boundary that matters

**There is no direct path from operator behavior back to Authority.**

That is one of the healthiest boundaries ARK has created.

- Behavior changes **interaction**
- Behavior never **rewrites truth**

Pressure First and Authority Adoption exist precisely to preserve this. Repeated sentences tighten workspaces and projections. They do not invent parallel stores or lifecycle authority because someone said *"I wish..."* once.

> **Every workspace should earn its shape through repeated operator behavior, not anticipated complexity.**

That sentence protects ARK from feature creep.

## What this is

Most business software has an interaction grammar, but it's **accidental**:

| Product type | Accidental grammar |
| --- | --- |
| CRM | Records + tabs |
| ERP | Modules + forms |
| Shop software | Lists + detail screens |
| EMRs | Charts + encounters |

Those grammars center the **database**. ARK is centering the **operator's questions**.

ARK is developing an **interaction language**, not a collection of mobile screens.

Every major operational object — Repair Order, Conversation, Inspection item, and eventually Customer, Vehicle, Vendor, Warranty — can be entered as a **workspace** that answers the same questions in the same order.

This is **explainable operations**: whether a suggestion comes from a simple rule, an observation, a recommendation engine, or eventually AI, the inspection surface does not change. It always answers:

> **Why did ARK suggest this?**

That consistency is more valuable than whether the suggestion was generated by an `if` statement or a model.

## The workspace stack

Sitting on top of projection, an **interaction stack** is emerging:

```
Object
  ↓
Workspace
  ↓
Orientation      (Where am I?)
  ↓
Health           (How is it?)
  ↓
Next             (What should I do?)
  ↓
Decision         (Why?)
  ↓
Memory           (What happened?)
  ↓
Commands         (What can I do?)
```

A new engineer can memorize this in five minutes.

**Memory** is the concept. **Timeline** is one implementation — the API may still say `timeline` while the philosophy says memory.

Inspection, Repair Order, and Conversation already fit this pattern. Customer, Vehicle, Vendor, and Warranty should follow the same grammar — not the same UI.

**Let multiple workspaces prove the grammar first.** Three strong examples exist today: Repair Order, Conversation, and Inspection. If Customer, Vehicle, and Vendor naturally converge on the same pattern over time, the grammar was **discovered** — not imposed.

## Seven questions every workspace answers

| # | Question | Layer | RO example | Conversation example |
| --- | --- | --- | --- | --- |
| 1 | **Who/what am I looking at?** | Orientation | `RO #1594 · Alex Rivera · 2016 Ram 2500 · Waiting Approval` | Customer + vehicle relationship context |
| 2 | **How healthy is it?** | Health | Inspection 72%, 2 recommendations ready, customer waiting | Customer waiting, advisor responded, last activity 4m ago |
| 3 | **What should happen next?** | Next | `NEXT: Check Cooling System` | Reply needed, follow up on estimate |
| 4 | **Why is ARK suggesting this?** | Decision | Rule + matched factors | Same shape everywhere |
| 5 | **What has happened?** | Memory | What has been done on this repair | What happened in this relationship |
| 6 | **What can I do?** | Commands | Photo, Finding, Complete Item | Reply, estimate link |
| 7 | **How confident is this workspace?** | Confidence | Dev/debug only today | Intentional gaps vs broken |

Question 4 — **Decision** — separates an assistant from an opaque system. A technician should always be able to answer *"Why?"* with one tap (eventually in-product; today via Workspace Inspector in debug builds).

Question 7 — **Confidence** — is for builders, not operators. It distinguishes *intentionally incomplete* from *broken*.

## Question-driven development

ARK is no longer asking *"What feature should we build?"*

ARK is asking **"Which question is the operator still asking?"**

| Operator asks… | Strengthen… |
| --- | --- |
| "Where am I?" | Orientation |
| "How is it going?" | Health |
| "What now?" | Next |
| "Why this?" | Decision |
| "What happened?" | Memory |
| "What can I do?" | Commands |

The roadmap stops being feature-driven and becomes **question-driven**.

Before adding a capability, ask: **Which operator question does this answer?** If it does not answer a recurring question — or answers one another layer already covers — it probably does not belong.

For **Evolution**, ask: **Which repeated sentence earned this change?** Not *"I think…"* Not *"We should…"* But *"We heard this five times."*

That keeps the roadmap grounded and keeps ARK cohesive as it grows.

## Orientation

Before someone can decide what to do, they have to **regain context**.

Orientation answers:

- Where am I?
- Who is this?
- Which vehicle?
- Which RO?
- What role am I in?

The persistent workspace header is not branding. It is the operator's **anchor**.

```
RO #1594
Alex Rivera
2016 Ram 2500
Waiting Approval
```

That is **Orientation**.

Orientation is identity and placement. It is not progress, posture, or recommendation pressure — those belong to Health.

---

## Health

**Health is the current operational posture of this object.**

It is not always a percentage. Resist progress bars everywhere.

| Workspace | Health examples |
| --- | --- |
| **Repair Order** | Inspection 72%, 2 recommendations ready, customer waiting |
| **Conversation** | Customer waiting, advisor responded, last activity 4m ago |
| **Vehicle** | 3 deferred repairs, maintenance overdue, battery healthy |
| **Vendor** | 2 overdue POs, awaiting shipment |

Health tells you how the object is doing **right now**. Orientation tells you **which object** you are looking at.

---

## Next

The Next engine must stay **humble**.

It is not a task manager. It must never say:

> Complete all these 12 things.

It answers one question:

> **If you only did one thing next, what should it be?**

That is cognitively much lighter. One suggestion. One tap. Move.

---

## Commands

The command bar must remain:

- **High-frequency** — what the operator reaches for without thinking
- **Context-aware** — relevant to this object and this moment
- **Role-aware** — technician muscle memory ≠ advisor muscle memory

Everything else belongs under **More**.

Muscle memory matters more than completeness. Do not let Commands become a toolbar full of everything.

---

## Memory

**Memory is what the operator wants. Timeline is how we often render it.**

Every workspace answers a memory question — not always as a chronological list:

| Workspace | Memory question |
| --- | --- |
| **Conversation** | What happened between us? |
| **Repair Order** | What has been done on this repair? |
| **Vehicle** | What has happened over its life? |
| **Inspection item** | What happened last time we checked this? |
| **Vendor** | What happened to this order? |

Render as timeline, activity feed, prior visits, or order history — the concept is **memory**. Do not confuse the implementation with the operator's question.

API payloads may use `timeline` as the transport key. Product language should say **memory**.

## Workspace payload grammar (conceptual)

Not a framework contract yet. Shape that RO workspace already projects:

```json
{
  "workspace": {
    "profile": "technician",
    "question": "What do I inspect next?",
    "orientation": {
      "number_label": "#1594",
      "customer_name": "Alex Rivera",
      "vehicle_label": "2016 Ram 2500",
      "status_label": "Waiting Approval"
    },
    "health": {
      "inspection": { "complete": 12, "total": 18 },
      "recommendations_ready_count": 2,
      "customer_posture_label": "Customer waiting"
    },
    "next": {
      "label": "Check Cooling System",
      "decision": {
        "question": "Why is NEXT suggesting Cooling System?",
        "rule": "CustomerWaitingSequentialOrder",
        "factors": [
          { "label": "Customer waiting", "matched": true },
          { "label": "Brakes complete", "matched": true },
          { "label": "Cooling System incomplete", "matched": true }
        ]
      }
    },
    "timeline": [ ],
    "command_bar": [ ],
    "confidence": { }
  }
}
```

Today RO workspace projects memory as `timeline` in the API. The conceptual split remains: **header = orientation**, health metrics below it = **health**, chronological entries = **memory**.

Notice what the payload does **not** say: `repair_order`, `conversation`, `inspection`. Those are specializations of the same grammar.

## Progressive disclosure by role

Workspaces differ by **what belongs in the repair**, not by permission theater.

| Role | Workspace excludes (by design) | Not because forbidden — because irrelevant |
| --- | --- | --- |
| **Technician** | Payments, reports, accounting, customer balance | Production grammar |
| **Advisor** | Inspection flow, production commands, next inspection item | Communication and decision grammar |
| **Manager** | Camera-first inspection, finding capture | Oversight grammar |

Permissions still exist. Workspace configuration is the cleaner philosophy.

## Decision explainability standard

**Current (RO workspace v1):** `question`, `rule`, `factors[]` with `matched: true`.

**Target (standardize everywhere):**

| Field | Purpose |
| --- | --- |
| **Suggestion** | What ARK recommends |
| **Rule** | Named rule (e.g. `CustomerWaitingSafetyPriority`) |
| **Matched factors** | ✓ Why this suggestion won |
| **Ignored factors** | What was considered but deprioritized |
| **Blocked by** | What prevents progress |
| **Confidence** | High / Medium / Low — qualitative, not numeric |
| **Alternatives considered** | Optional; human-readable only |

**Example:**

```
Suggestion:     Cooling System
Rule:           CustomerWaitingSafetyPriority
Matched:        ✓ Customer waiting
                ✓ Brakes complete
Ignored:        • Cosmetic concern
Blocked:        • Engine not inspected
Confidence:     High
```

### Do not expose

- Weights, scores, priority floats (`priority = 0.73`)
- Implementation internals

Explain **reasoning**, not **implementation**. Nobody on the floor thinks in decimals.

## Confidence maturity

**Today (development):** `Workspace Ready: 86%` + list of intentional Phase 3 gaps.

**Target:** Granular capability catalog — easier to reason about than one percentage.

| Symbol | Meaning |
| --- | --- |
| **✓** | Complete |
| **△** | Partial |
| **○** | Planned |

Example:

```
Navigation         ✓
Inspection Flow    ✓
Conversations      ✓
History            △
Voice              ○
Camera             △
```

Confidence is for **builders**, not users.

## Build sequence: phone first

```
Phone → observe → refine → scale to desktop
```

Not: desktop → shrink to mobile.

Mobile is the proving ground for workspace grammar. **Do not port to web until product questions are answered on the floor.**

### What to build next

Not new capabilities. **Friction removal.**

Daily question: *What took three taps that should have taken one?*

| Repeated sentence | Fix type |
| --- | --- |
| "I keep hitting Save & Next with greasy gloves." | Bigger Save — not redesign inspection |
| "I always open Conversation after Overview." | Reorder sections — not a new feature |
| "I take three photos before adding a measurement." | Camera stays open — not a new screen |

### What not to build next

- AI summaries
- Push notifications
- ARK Voice
- Desktop workspace parity
- More settings
- Premature framework abstraction

## Observation notebook

**Observe first. Instrument confirms — it does not replace.**

Eventually someone will say: *"Let's instrument all of this."* Instrumentation is valuable. It should **confirm** notebook observations, not discover them.

| Sequence | Right | Wrong |
| --- | --- | --- |
| 1 | Notebook: *"I always ignore NEXT after brakes."* | Dashboard shows low NEXT tap rate — now what? |
| 2 | Instrumentation: Is that true across five technicians? | Instrument first, explain later |

The notebook preserves **context**. Metrics preserve **scale**. Never reverse the order.

**Do not graph for its own sake. Do not optimize before observing.**

### End-of-day confidence question

Ask Landon (and later Molly):

> **"Did ARK ever make you uncertain about what to do next?"**

Not "Did you like it?" Not "Was it fast?" **Uncertainty** is the metric underneath NEXT, workspaces, and inspection flow.

## Two design tests

Hesitation and momentum are related but **independent**.

### Hesitation test

> Does the operator know what to do next?

If not, **Orientation**, **Health**, **Next**, or **Decision** need work.

End-of-day question for Landon:

> **"Did ARK ever make you uncertain about what to do next?"**

### Momentum test

> Can they keep doing it without losing context?

If not, **navigation**, **back stack**, **camera flow**, **auto-save**, or **workspace shell** need work.

You can know what to do next and still lose momentum because you bounced through four screens.

### What protects momentum

These are not really "features." They protect continuous work:

- Persistent header (orientation anchor)
- Save & Next
- Auto-advance to next inspection item
- Sticky command bar
- No nested back stacks
- Camera persistence (planned)
- Tablet tri-pane (partial)
- Conversation staying inside the RO workspace

When evaluating a change, run **both** tests.

## Philosophy

### Product purpose

> **The purpose of ARK is not to digitize shop operations. It is to reduce hesitation while preserving momentum, using operational truth that remains explainable at every step.**

That is not a mobile philosophy or a workspace philosophy. It is **product philosophy** — it applies to inspections, communications, telephony, scheduling, customer portals, and products not yet imagined.

### Workspace principles

A workspace exists to **reduce hesitation**.

A workspace should **preserve momentum**.

They are companions, not duplicates:

| Principle | Means |
| --- | --- |
| **Reduce hesitation** | I know what to do |
| **Preserve momentum** | I don't lose my place while doing it |

A good workspace answers the questions an operator naturally asks — in the order they ask them. Every additional screen, search, or decision introduces hesitation. Every unnecessary navigation break kills momentum.

ARK workspaces should continually evolve toward:

1. Making the next correct action **obvious**
2. Making the reasoning behind that action **inspectable**
3. Letting the operator **stay in the work** without bouncing out

### Four grammars, one system

| Grammar | Keeps ARK… |
| --- | --- |
| **Authority** | Truth coherent |
| **Projection** | Audiences coherent |
| **Workspace** | Interaction coherent |
| **Evolution** | Product coherent |

The next five years of ARK do not depend on remembering every design conversation. They depend on asking the same small set of questions, observing real work, and letting the answers tighten the product.

Six months from now, contributors will not remember why there are persistent headers, why NEXT exists, or why the Workspace Inspector shows rules instead of scores. These sentences tie those decisions together:

> **Reduce hesitation. Preserve momentum. Make the next action obvious. Make the reasoning inspectable.**

**Continuous Work** is the north star. If a technician never pauses to figure out the software — and never loses their place while using it — ARK has become part of the repair instead of an interruption to it.

If the answer to the end-of-day hesitation question is consistently **"No"** — the grammar is working.

The next milestone is not another feature. It is **Landon on the floor** — repeated sentences in the notebook, tightening only what earned it, and letting the evolution loop do its work.

## PR doctrine review

From here, the biggest risk is not under-design. It is **violating the philosophy**.

Every **significant PR** must answer four questions — architectural linting:

| Grammar | Question |
| --- | --- |
| **Authority** | What truth changed? |
| **Projection** | Who sees this differently? |
| **Workspace** | Which operator question does this answer? |
| **Evolution** | Which repeated sentence earned this? |

If a PR cannot answer all four, it probably is not ready.

Human reviewers should act as **doctrine reviewers**, not only implementers. See companion doctrine `ark-pr-doctrine-review`.

### Reviewer output shape

```
Authority     ✓ No duplicate truth
Projection    ✓ Existing projection reused
Workspace     ✓ Reduces hesitation · ✓ Preserves momentum
Evolution     ⚠ No repeated sentence cited → Observe before building
```

## Earned Intelligence

**Anti-pattern:** Premature Intelligence — answering a question nobody is asking yet.

**Principle:** Intelligence is introduced only after authority is trusted and the repeated operator question has been observed.

Examples of premature intelligence: AI summaries before sentences; push before polling fails; desktop parity before phone workspace stabilizes.

When someone says *"We should add AI here"* — the answer is:

> **"What repeated sentence earned it?"**

See doctrine `ark-earned-intelligence.mdc.`

## The question going forward

Stop asking **"What's next?"**

Ask **"What has earned the right to exist?"**

ARK has learned how to say no. Preserving coherence while the product grows is the hardest part of building software — and the capability ARK is now positioned to protect.
